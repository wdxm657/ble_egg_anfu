## 1. 架构概览

```
┌─────────────┐    BLE GATT        ┌──────────────┐    UART 55AA+CRC16    ┌──────────────────┐
│  手机 APP    │ ◄──────────────► │  TLSR8258 MCU  │ ◄─────────────────► │  STAR373 SOC     │
│  (visializable│    Ctrl RX/TX    │  (app_ctrl)   │    115200 8N1       │  (dog_soother)    │
│   .py)       │                   │  (app_uart)   │                     │  (uart_proto)     │
└─────────────┘                   └──────────────┘                     └──────────────────┘
```

## 3. 联调阶段划分

### 阶段一：MCU ↔ SOC UART 基础通信（预计 1 天）

**目标**：确保 MCU 与 SOC 间 UART 帧能正常收发、CRC 校验正确、序列号匹配。

**前置条件**：
- MCU 固件烧录至 TLSR8258 开发板（`ble_egg_anfu` 工程）
- SOC 端 `dog_soother` 可执行文件部署至 RV1103G1
- UART 物理连接（MCU PD3=TX, PD2=RX, 115200 8N1）
- SOC 端串口设备路径确认（当前默认 `/dev/ttyS1`，可通过 `-D` 参数或 `DS_UART_DEVICE` 环境变量指定）

**关键设计——心跳机制**：

SOC 启动后通过 `bark_control_tick()` 每 **2 秒** 发送一次 `HEARTBEAT_EVT(0x87)`（EVT 帧，空 payload）。
MCU 在 `app_ctrl_time_task()` 中监控：
- 收到心跳 → `g_soc_online = 1`
- 超过 **7 秒** 未收到心跳 → `g_soc_online = 0`
- **所有** BLE 命令在执行前调用 `app_ctrl_check_soc_online()` 检查，若 SOC 离线则直接回复 `SOC_TIMEOUT(0x09)` 错误码，**不向 UART 转发**。
- `UID_GET` 从本地 Flash 读取，但 SOC 离线时也返回 `SOC_TIMEOUT`，避免 APP 获取到过期数据。

**测试步骤**：

| 步骤 | 操作 | 预期 | 验证方法 |
|------|------|------|---------|
| 1.1 | 上电，MCU 初始化后 `app_uart_init()` 配置 UART | GPIO 初始化完成 | 逻辑分析仪看波形 |
| 1.2 | MCU 调用 `app_ctrl_init()`，注册 EVT 回调 | 心跳、WORK_STATE、OWNER_REC 三个 handler 已注册 | 代码静态确认 |
| 1.3 | **仅 MCU 上电，SOC 未启动**，APP 发 STATUS_GET | MCU 直接回 `SOC_TIMEOUT(0x09)`，UART 无输出 | 上位机收到 `status=0x09` |
| 1.4 | SOC 端启动 `dog_soother`（`uart_proto_open` + `start_rx`） | UART 端口打开，RX 线程启动 | SOC 日志 `uart open success` |
| 1.5 | SOC 启动后约 2 秒内发送 `HEARTBEAT_EVT(0x87)` | MCU 收到 `[SOC_FRAME] t=0x03 cmd=0x87` 并置 `g_soc_online=1` | MCU BLE_LOG_D 输出 |
| 1.6 | SOC 在初始化后主动发 `WORK_STATE_EVT(0x80)` | MCU 收到后 `app_ctrl_evt_work_state_from_soc` 被调用 | MCU 日志 `[SOC_FRAME]` |
| 1.7 | SOC 运行中，每隔约 2 秒持续发 HEARTBEAT_EVT | 心跳周期性的在 SOC 日志可见 `uart_tx: 55 AA 01 03 87 ...`，MCU 侧 `g_soc_online` 保持 1 | 双方日志 |
| 1.8 | 断开 SOC 与 MCU 的 UART 连接（或停止 SOC 程序） | MCU 超过 7 秒未收到心跳，`g_soc_online` 自动置 0 | 上位机发 STATUS_GET 应收到 `0x09` |
| 1.9 | 重新启动 SOC，心跳恢复 | MCU 再次置 `g_soc_online=1`，BLE 命令正常 | 上位机命令恢复正常 |

**关键检查点**：
- CRC16-IBM 校验一致（MCU 侧 `app_uart_crc16_ibm` ↔ SOC 侧 `uart_crc16_ibm`）
- 帧头 `0x55 0xAA` 同步正常
- 序列号递增无冲突

### 阶段二：BLE APP ↔ MCU 基础命令联调（预计 2 天）

**目标**：通过上位机 `visializable.py` 或手机 APP，验证 BLE 全双工通信。

**前置条件**：
- 阶段一完成，MCU↔SOC UART 通信正常
- 上位机 Python 环境（`bleak`, `PyQt5`）
- BLE MAC 地址已知（可用手机扫描 `SincereEGGA` 获取后填入）

**测试清单**：

#### 2.1 POWER_CTRL (0x12)

| 操作 | 预期 RSP |
|------|---------|
| 发送 `[0x01]`（开机） | `[0x00, 0x01]` |
| 发送 `[0x00]`（关机） | `[0x00, 0x00]` |
| 发送空 payload | `[0x03, 0x00]`（PARAM_ERROR） |

**注意**：POWER_CTRL 依赖 SOC 在线检查（SOC 离线返回 `SOC_TIMEOUT`），等 SOC 回包后才回复 APP。需要验证：
- SOC 回包 `[status, onOff]` 中的 `onOff` 与请求一致
- MCU 侧 `g_ctrlState.powerState` 同步更新
- 关机后重开机能恢复监测状态（`workState` 置 1）

#### 2.2 STATUS_GET (0x13)

| 操作 | 预期 RSP |
|------|---------|
| 发送空 payload | `[0x00, powerState, workState, 0x01, ownerVoiceExist, volume, calmMode, enabledMask, usMask]` |

**注意**：该命令等待 SOC → UART → 回调 → 回 APP 全链路。联调时可借助 `DS_UART_DEBUG=1` 在 SOC 端打印收发帧 hex。

**数据结构对应**：
```
RSP[0] = status (0x00=OK)
RSP[1] = powerState    (MCU 本地维护)
RSP[2] = workState     (来自 SOC)
RSP[3] = btLinked      (固定 1)
RSP[4] = ownerVoiceExist (来自 SOC)
RSP[5] = volume        (来自 SOC)
RSP[6] = calmMode      (来自 SOC)
RSP[7] = enabledMask   (来自 SOC)
RSP[8] = usMask        (来自 SOC)
```

#### 2.3 VOLUME_SET (0x14) / VOLUME_GET (0x15)

| 操作 | 预期 RSP |
|------|---------|
| VOLUME_SET `[15]` | `[0x00, 15]` |
| VOLUME_SET `[31]`（超范围） | `[0x03, 0x00]`（PARAM_ERROR） |

**注意**：`VOLUME_GET` 向 SOC 查询后返回，SOC 回包 `[status, volume]` 中的 `volume` 为 SOC 实际音量值。

## 4. 已知问题 / 风险 / 待办

### 4.1 MCU 侧

| # | 问题 | 影响 | 建议处理时机 |
|---|------|------|------------|
| 0 | **SOC 在线心跳机制**：SOC 每隔 ~2s 发 HEARTBEAT_EVT(0x87)，MCU 超时 7s 未收到则标记 SOC 离线。**所有** BLE 命令前置检查 `g_soc_online`，离线时直接回 `SOC_TIMEOUT(0x09)` | ✅ 已实现，联调阶段一验证即可 | 阶段一 |
| 1 | ~~`POWER_CTRL` 不等待 SOC 回包~~ | ✅ 已修复：改为 `app_uart_send_cmd_with_cb` 等待 SOC 回包后回复 APP | 阶段二 |
| 2 | `CALM_MODE_GET` 复用 `STATUS_GET` 的 UART CMD 0x11 | `calmMode` 从 STATUS_GET 的第 7 字节提取，但未同步 `measureOrder/usOrder` | 如需完整策略信息，建议走 `CALM_STRATEGY_GET` |
| 3 | `app_uart_pending` 槽位最多 8 个 | 频繁并发请求可能占满 | 观察日志中 `slot < 0` 告警 |
| 4 | `TEXT_CHUNK(0x40)` BLE 日志分片发送有 `sleep_us` 延时 | ATT 队列可能溢出 | 正常使用影响不大 |
| 5 | MCU 时间缓存仅 `clock_time()` tick 自增 | 长时间运行会有误差 | 配合 TIME_SET 定期同步 |

### 4.2 SOC 侧

| # | 问题 | 影响 | 建议处理时机 |
|---|------|------|------------|
| 1 | `bark_control` 自动安抚状态机部分逻辑仍为占位 | 自动安抚流程不完整 | 阶段三联调前补全 |
| 2 | `ultrasonic` 模块为占位 | 超声发射功能不可用 | 阶段三联调前补全 |
| 3 | 时区设置仅运行期生效 | 重启后丢失 | 后续迭代优化 |
| 4 | AO 播放双声道 downmix 为兼容方案 | 真双声道场景需复核 | 后续迭代优化 |

### 4.3 联调中发现问题的快速定位方法

```
问题: APP 发命令后无响应
  ├─ 检查 BLE 连接状态（visializable 显示"已连接"？）
  ├─ 检查 MCU 日志（DEBUG_MODE 开启时 BLE_LOG_D 输出）
  │    ├─ 有 [SOC_FRAME] 日志 → MCU 收到了 SOC 回复，问题在 BLE Notify
  │    └─ 无 [SOC_FRAME] 日志
  │         ├─ MCU 发 UART 了吗？→ 检查 UART 物理连接
  │         └─ SOC 端 DS_UART_DEBUG=1 看是否有帧进来
  │              ├─ 有进无出 → SOC 侧 uart_dispatch switch 没命中
  │              └─ 无进 → 波特率/引脚/电平不匹配
  └─ 使用逻辑分析仪抓 UART TX/RX 引脚
```

```
问题: SOC 端日志正常但 MCU 未转发到 APP
  ├─ MCU 侧 BLE_LOG_D("[SOC_FRAME]") 是否打印？
  │    └─ 已到 → 检查 app_uart_dispatch_rsp 回调匹配
  │         └─ cmdId/seq 匹配不上 → pending 槽位被提前回收
  └─ 未到 → CRC 校验失败（看 crc_err 日志）
```

## 6. UART 帧格式速查

### 6.1 通用帧格式

```
Byte[0] = 0x55           // sync header
Byte[1] = 0xAA           // sync header
Byte[2] = ver (0x01)     // protocol version
Byte[3] = msgType        // 0x01=REQ, 0x02=RSP, 0x03=EVT
Byte[4] = cmdId
Byte[5] = seq
Byte[6] = payloadLen & 0xFF
Byte[7] = (payloadLen >> 8) & 0xFF
Byte[8..8+payloadLen-1] = payload
Last 2  = CRC16-IBM(Byte[2..8+payloadLen-1])  // 小端
```

### 6.2 BLE 帧格式

```
Byte[0] = ver (0x01)
Byte[1] = msgType         // 0x01=CMD, 0x02=RSP, 0x03=EVENT
Byte[2] = cmdId
Byte[3] = seq
Byte[4] = payloadLen & 0xFF
Byte[5] = (payloadLen >> 8) & 0xFF
Byte[6..] = payload
```

**注意**：BLE 帧无 `0x55 0xAA` 头和 CRC（由 ATT 层保证）。
